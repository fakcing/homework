# Dogfight — Lab 01: The Event Loop Is the Game Loop

Космічний корабель на canvas, який літає на фіксованому кроці симуляції 60 Гц з інтерполяцією рендеру.
Тема: космічні кораблі (фізика та мережа однакові для будь-якої теми).

## Запуск

```bash
nvm use            # Node 22 (.nvmrc)
npm install
npm run dev        # http://localhost:5173
npm run lint       # ESLint (+ заборона window/document/performance у src/sim)
npm run format     # Prettier
npm test           # node:test — чистота integrate, wrap-around, кути
```
 
Керування: `←/→` або `A/D` — поворот, `↑` або `W` — тяга.

## Структура

```
src/
  main.js            складання: input + sim + render + loop; перемикачі експериментів
  loop.js            createLoop({ step, simulate, render }) — rAF + акумулятор із clamp
  input.js           createInput(target) — замикання; isDown / justPressed / endStep
  math.js            lerp, wrapCoord, shortestDelta, shortestAngleDelta
  sim/               БЕЗ DOM/canvas (ESLint це перевіряє)
    ship.js          createShip, integrate(ship, input, dt) — чиста функція
    arena.js         ARENA, wrapShip
    step.js          advance = wrapShip ∘ integrate
  render/

    interpolate.js   lerp позиції (через шов wrap) та кута (найкоротша дуга)
    draw.js          фон, зірки, корабель + «привиди» на краях, HUD
scripts/determinism.mjs   Експеримент 3 у Node
```

## Дизайн-рішення

- **Фіксований крок.** `simulate(1/60)` викликається рівно 60 разів/с незалежно від дисплея; `dt` кадру обрізається до 0.25 с (немає «спіралі смерті»).
- **Інтерполяція.** Зберігаю `prev` і `curr`; рендер малює `lerp(prev, curr, alpha)`, `alpha = accumulator / step`. Позиція інтерполюється найкоротшим шляхом через край арени, кут — найкоротшою дугою (інакше при переході ±π корабель «крутнеться» на 360°).
- **Ввід як замикання.** `down`/`pressed` приватні; `justPressed` очищається після кожного _кроку симуляції_, а не кадру — натискання бачить рівно один крок і на 120 Гц, і після фрізу.
- **Фізика.** Напівнеявний Ейлер, drag як `exp(-k·dt)` (не залежить від `dt`), обмеження швидкості. Логічна арена фіксована, тому симуляція не залежить від розміру вікна.
- **Тюнінг.** Початково `turnRate 3.6`, `thrust 420`, `drag 0.8`, `maxSpeed 600`. _Що змінив і чому:_ ___ (запиши 2–3 пункти після польоту).

## Експерименти «зламай і поміряй»

Перемикачі в URL: `?exp=block`, `?exp=interval`, `?exp=variable`, `?load=<мс>` (додаткове навантаження на кадр), `?auto` (віртуальний ввід: тяга + поворот, лог позиції на 5-й секунді симуляції).

### 1. Блокуючий цикл у `render` (`?exp=block`)

100 мс busy-wait кожен 60-й кадр.

| Метрика              | Норма   | З блокуванням                      |
| -------------------- | ------- | ---------------------------------- |
| steps/s              | 60.0    | 60.2                               |
| frames/s             | 144.0   | 118.4                              |
| frame time (max)     | 7.0 мс  | 97.2 мс (σ 11.55)                  |
| work (кадр з блоком) | 0.20 мс | ≈ 100 мс (0.30 у звичайних кадрах) |

Що бачить гравець: раз на секунду ___ (мікро-фриз, корабель «підстрибує» — за один кадр акумулятор виконує ~6 кроків, бо 100 мс / 16.7 мс ≈ 6).

**Пояснення.** JS має один потік і виконує задачу до завершення (run-to-completion). Поки `while` крутиться, стек викликів не порожній, тож event loop не може взяти наступну задачу, не може запустити rAF-колбеки, а браузер — виконати layout/paint. Таймери, події клавіатури й мережа лише стають у чергу. Із того ж потоку цього не обійти: ніякий JS-код не може перервати сам себе. Єдині виходи — розбити роботу на менші шматки або винести її в інший потік (Web Worker).

### 2. `setInterval(frame, 16)` замість rAF (`?exp=interval`)

| Метрика                     | rAF                 | setInterval(16)      |
| --------------------------- | ------------------- | -------------------- |
| frames/s (10 с)             | 144.0               | 62.5                 |
| frame time, σ (jitter), max | σ 0.05 / max 7.0 мс | σ 0.60 / max 17.7 мс |
| фонова вкладка 5 с          | ___                 | ___                  |

**Пояснення.** 16 ≠ 16.667 мс, тож інтервал дрейфує відносно vsync: частина тіків потрапляє на кадр двічі, частина — жодного, звідси більший jitter. Колбек `setInterval` — це task, а не крок рендерингу: він не знає про момент paint, і на дисплеї 120/144 Гц він все одно дає ≈62 Гц. У фоновій вкладці браузер тротлить таймери (≥1 с), тоді як rAF там повністю призупиняється й не витрачає CPU. Завдяки clamp гра після повернення не «телепортується».

### 3. Змінний крок замість фіксованого (`?exp=variable`)

Браузер: `?exp=variable&auto&load=0` та `?exp=variable&auto&load=30` (імітація слабкої машини) — порівняти з `?auto` (fixed) при тих самих `load`. Скопіюй рядок `[…] auto @ … x= y=` з консолі:

| Режим             | Кроків | x (5 с)  | y (5 с)  |
| ----------------- | ------ | -------- | -------- |
| fixed, load=0     | 300    | 799.3141 | 390.1615 |
| fixed, load=30    | 300    | 799.3141 | 390.1615 |
| variable, load=0  | 715    | 800.9328 | 387.8761 |
| variable, load=30 | 157    | 795.3631 | 396.9129 |

Те саме для 6× CPU throttle у DevTools (Performance → CPU: 6× slowdown).

Детермінований прогін у Node (`npm run exp:determinism`, ті самі `advance`/`integrate`, синтетичні тривалості кадрів, 5 с симуляції):

```
FIXED step
  60 Hz (16.67 ms)                 steps=300  x=799.314074  y=390.161457
  144 Hz (6.94 ms)                 steps=300  x=799.314074  y=390.161457
  slow (100 ms)                    steps=300  x=799.314074  y=390.161457
  hitch (400 ms, clamped to 250)   steps=300  x=799.314074  y=390.161457

VARIABLE step
  60 Hz (16.67 ms)                 steps=300  x=799.314074  y=390.161457
  144 Hz (6.94 ms)                 steps=720  x=800.864462  y=387.157209
  slow (100 ms)                    steps= 50  x=784.621077  y=413.857842
  hitch (400 ms, clamped to 250)   steps= 20  x=753.290726  y=447.547352
```

**Пояснення.** rAF-колбек викликається з тією частотою, з якою браузер встигає малювати; якщо задача довга, кадр приходить пізніше. При `simulate(dt)` раз на кадр траєкторія залежить від того, як event loop розклав кадри в часі, а інтегратор (Ейлер, clamp швидкості, поворот) не інваріантний до `dt`. З акумулятором кількість і розмір кроків завжди однакові → результат ідентичний до біта. Для мультиплеєра (Lab 5) це вимога: клієнт і сервер мають отримувати той самий стан із того самого вводу.
